## Goal

M4 turns the M2/M3 core into a working local daemon. `runtime/core` gains a `shelf`-based `/v1` HTTP server with token authentication and scopes, a `0600` token file, pairing, and an SSE endpoint that replays and deduplicates by `seq`; the M2 `StatePublisher` backpressure limitation is closed here. `runtime/cli` and `runtime/bin` become a real `alterione` binary — `serve`, `status`, `run`, `chat`, `watch`, and `doctor` — wired through `runtime/bin` to the core `serve` composition. The daemon resolves XDG/`ALTERIONE_HOME` paths, holds a single-instance lock, and shuts down gracefully on SIGTERM; on Windows it runs as a logon task (ADR-0009, T20). The four section 2.8 target metrics are measured and recorded (#49), and an e2e local-mode test drives a real daemon, a real client, and a fake `LlmPort`. Remote mode (TLS, certificate fingerprint pinning, pairing rate limit, CLI contexts) stays in M4b.

## Acceptance criteria

- [ ] The `shelf` `/v1` server serves `/v1/info` and `/v1/health`, checks the `Host` allowlist, enforces body limits (32 KB run input, 256 KB otherwise), and binds `127.0.0.1` (verified by `runtime/core/test/infrastructure/server/http_api_test.dart`).
- [ ] Token auth: the daemon creates `~/.config/alterione/token` at mode `0600`; a request without a valid bearer token gets 401 and a valid token with an insufficient scope gets 403 (verified by `runtime/core/test/infrastructure/server/auth_test.dart`).
- [ ] Pairing: `POST /v1/pair` exchanges a one-time code (valid 2 minutes, single use) for a device token; an expired or reused code is rejected (verified by `runtime/core/test/infrastructure/server/pairing_test.dart`).
- [ ] REST resources: `POST/GET /v1/runs`, `:cancel`/`:pause`/`:resume`, `GET /v1/approvals`, `POST /v1/approvals/{id}`, and `GET /v1/extensions` behave and enforce scopes (verified by `runtime/core/test/infrastructure/server/resources_test.dart` and golden JSON).
- [ ] SSE with replay: `/v1/events?since=` and `Last-Event-ID` replay from the journal, deduplicate by `seq`, never replay `run.delta`, and send a `: ping` every 15 s (verified by `runtime/core/test/infrastructure/server/sse_test.dart`).
- [ ] Q16 resolved: `RunStarted`, `RunFinished`, and the approval events carry a non-null monotonic `seq` that SSE can replay (verified by a journal lifecycle test and the SSE replay test; recorded in a new ADR).
- [ ] `packages/client` speaks REST and SSE, reconnects from `since`, and surfaces `UnknownEvent` without failing (verified by `packages/client/test`).
- [ ] Daemon lifecycle: `alterione serve` loads configuration, opens the journal, and holds a single-instance lock in the data directory (a second instance exits with a clear message and a non-zero code); on SIGTERM it answers new runs with `503 shutting_down`, finishes tool calls (30 s cap), marks unfinished runs `interrupted`, publishes `server.shutdown`, unloads extensions, flushes Hive, and releases the lock (verified by `runtime/core/test/infrastructure/daemon_test.dart`, including SIGTERM during a tool call).
- [ ] XDG/`ALTERIONE_HOME` paths: config, data, and cache resolve from the XDG defaults, `ALTERIONE_HOME` overrides the root, and the journal directory is passed to `registerJournal` (verified by `runtime/core/test/infrastructure/paths_test.dart`).
- [ ] CLI `status`, `run`, `chat`, `watch`, and `doctor`, plus `serve` wired through `runtime/bin`; `--json` is supported; exit codes are 0/2/3/4/5; a stopped daemon is reported with a suggestion to run `serve` (verified by `runtime/cli/test` and a `runtime/bin` smoke test).
- [ ] `doctor` checks the daemon, the token and its rights, configuration validity, extension signatures, provider availability, that `llama-server` has no tools (`GET /tools`, 404 tolerated per Q20), and that the binary matches its `distribution.yaml` (verified by `runtime/cli/test/doctor_test.dart`).
- [ ] Windows logon task: the Task Scheduler task at logon runs `alterione serve`; the stop path without SIGTERM triggers the same graceful shutdown; the `%APPDATA%` mapping is documented (verified by a path-mapping unit test; the Task Scheduler registration is a manual gate, T20).
- [ ] Section 2.8 metrics are measured and recorded: cold start < 300 ms, idle memory < 80 MB (minimal build), event delivery latency p99 < 50 ms, tool-call overhead < 5 ms (verified by the Step 13 harness and its report; tracked by #49).
- [ ] e2e local-mode: a real daemon on a temporary `ALTERIONE_HOME`, a real client, and a fake `LlmPort` complete a chat and an SSE replay (verified by `e2e/test`).
- [ ] `melos run ci` equivalent is green via the per-package commands below, and `docs_check` exits 0.

## Steps

One tracking issue should be filed before implementation; its body is the checklist below. Steps are ordered by dependency: the HTTP API and its auth land in `runtime/core` first, then the client, the daemon composition and shutdown, the CLI, and finally the platform, metrics, and e2e work. `melos` is broken in this container (see M3.md), so every step uses the per-package commands in Acceptance commands.

Risks and dependencies: the SSE step depends on the Q16 ADR decision; the client and CLI depend on the server's wire contract (golden JSON); the metrics and e2e steps depend on a running daemon; T11/T20 cannot be fully verified on Linux and remain manual gates; the `transcripts` box (Q15) is a seam the transcript endpoint must not fake.

### Part 1 — HTTP API and server core (`runtime/core`)

- [ ] Step 1: Add the `shelf` `/v1` server foundation in `runtime/core/lib/src/infrastructure/server/` — `HttpApi` (a `shelf` `Router`) serving `GET /v1/info` (protocol version, sdk, capabilities) and `GET /v1/health`, a `Host` allowlist middleware (`localhost`, `127.0.0.1` in local mode), request body limits (32 KB for run input, 256 KB otherwise, `413` on overflow), and a bind helper on `127.0.0.1`. Export the type from `runtime/core/lib/alteri_one_core.dart`. No authentication yet. Tests: `runtime/core/test/infrastructure/server/http_api_test.dart` (info/health, foreign `Host` rejected, oversize body rejected).
- [ ] Step 2: Add path resolution in `runtime/core/lib/src/infrastructure/paths.dart` — a `HomePaths` value that resolves config (`~/.config/alterione`), data (`~/.local/share/alterione`, Hive and lock file), and cache (`~/.cache/alterione`) from the XDG defaults, with `ALTERIONE_HOME` overriding the root for all three, and a helper returning the journal directory. Document that Windows `%APPDATA%` mapping is T20 (Step 12). Tests: `runtime/core/test/infrastructure/paths_test.dart` (XDG defaults, `ALTERIONE_HOME` override, journal directory). This is the Q10 seam: the daemon calls `registerJournal(directory: ...)` and owns the path and lifetime.
- [ ] Step 3: Add the token file and bearer authentication in `runtime/core/lib/src/infrastructure/server/` — a `TokenStore` that creates `<config>/token` at mode `0600` on first start, an auth middleware that parses `Authorization: Bearer` and maps a token to a device and its scopes, and the scope vocabulary (`read`, `read.io`, `run`, `approve`, `admin`). Missing or invalid token → 401; valid token without the scope → 403. Tests: `runtime/core/test/infrastructure/server/auth_test.dart` (0600 mode, 401, 403).
- [ ] Step 4: Add pairing in `runtime/core/lib/src/infrastructure/server/pairing.dart` and the `POST /v1/pair` route — a one-time code valid for 2 minutes, single use, exchanged for a device token; the response shape carries the server certificate fingerprint field used by M4b. A small device registry supports list/revoke. Tests: `runtime/core/test/infrastructure/server/pairing_test.dart` (valid code issues a token; expired and reused codes rejected).
- [ ] Step 5: Wire the REST resources in `runtime/core/lib/src/infrastructure/server/routes.dart` to `RunService`, `StatePublisher`, and `ApprovalsBloc` — `POST /v1/runs`, `GET /v1/runs`, `GET /v1/runs/{id}`, `:cancel`/`:pause`/`:resume`, `GET /v1/approvals?pending=`, `POST /v1/approvals/{id}`, and `GET /v1/extensions`, each with the scope the spec assigns. Golden JSON files pin the DTO shape (`contracts.md` §10). Tests: `runtime/core/test/infrastructure/server/resources_test.dart` plus golden files. If the diff is too large for one review, split runs and approvals into two PRs and record the split as an added step.
- [ ] Step 6: Resolve Q16 and add a run-lifecycle record in `runtime/core/lib/src/infrastructure/journal/hive_journal.dart` — extend `JournalPort` and the `HiveJournal` so run start/finish and approval requests/decisions receive a real `seq` from the shared counter (a `kind: lifecycle` discriminator alongside `tool` and `model`), and make `RunService` publish `RunStarted`, `RunFinished`, and the approval events with that `seq` instead of `null`. Write the decision as a new ADR in `docs/adr/`, update `docs/spec/storage.md` §15.1 and `docs/spec/open-questions.md` Q16. Tests: `runtime/core/test/infrastructure/hive_journal_test.dart` (lifecycle round-trip and monotonic `seq`) and an updated `runtime/core/test/application/run_service_test.dart` (non-null `seq`).
- [ ] Step 7: Add the SSE transport in `runtime/core/lib/src/infrastructure/server/sse.dart` and the `GET /v1/events?since=` route — subscribe to live `StatePublisher` events, replay from the journal after `since`/`Last-Event-ID`, and deduplicate by `seq` (the order the spec fixes); never replay `run.delta`; send a `: ping` comment every 15 s; apply its own backpressure so a slow consumer is bounded (closes the M2 `StatePublisher` T15 limitation). Tests: `runtime/core/test/infrastructure/server/sse_test.dart` (replay, dedup, order, `run.delta` excluded, ping, backpressure).

### Part 2 — Client, daemon, CLI, platform, acceptance

- [ ] Step 8: Implement `packages/client` (currently a scaffold) — an HTTP+SSE client over `package:http` depending only on `contracts` and `http`, with REST methods, an SSE reader that reconnects from `since`/`Last-Event-ID`, and event mapping that surfaces `UnknownEvent` instead of throwing. Export from `runtime/../packages/client/lib/alteri_one_client.dart`. Tests: `packages/client/test/client_test.dart` and `packages/client/test/sse_test.dart`.
- [ ] Step 9: Add the daemon composition and lifecycle in `runtime/core/lib/src/application/daemon.dart` (or `infrastructure/daemon/`) — load configuration (section 14 merge, including `ALTERIONE_*` environment variables), open the journal, register the profile, start the shelf server, acquire a single-instance lock in the data directory (a second instance exits with a clear message and a non-zero code), and handle SIGTERM with the section 18.2 sequence: `503 shutting_down` for new runs, finish tool calls (30 s cap), mark unfinished runs `interrupted`, publish `server.shutdown`, unload extensions, flush Hive, release the lock. Tests: `runtime/core/test/infrastructure/daemon_test.dart` (SIGTERM during a tool call; 503; interrupted runs; lock released).
- [ ] Step 10: Implement the CLI command library in `runtime/cli/lib/src/commands/` — `status`, `run` (`--mode`, `--profile`, `--follow`), `chat` (interactive, streaming), `watch` (live events with approvals in the terminal), and `doctor` (checks below), plus `--json` and the exit codes 0/2/3/4/5. Use only `alteri_one_client` and `alteri_one_contracts`; a stopped daemon is reported with a suggestion to run `serve` and never starts a second core. Tests: `runtime/cli/test/commands_test.dart` against a fake HTTP server/fake client.
- [ ] Step 11: Wire `runtime/bin` — replace the `bin/alterione.dart` scaffold with argument parsing that dispatches commands to `alteri_one_cli` and routes `serve` to the core daemon; keep business logic out of `runtime/bin`. Add a `runtime/bin` smoke test that runs `alterione --help`, `alterione status` against a stopped daemon (exit code 3), and `alterione serve` startup/shutdown.
- [ ] Step 12: Implement the Windows logon task (ADR-0009, T20) — the `alterione service install`/`uninstall`/`status` commands register a Task Scheduler task at user logon that runs `alterione serve`; add a stop path that does not rely on SIGTERM (named event or IPC endpoint) which triggers the same graceful shutdown; document and unit-test the `%APPDATA%`→config/data directory mapping. The Task Scheduler registration itself is a manual gate. Tests: a path-mapping unit test; a documented manual checklist for the task registration.
- [x] Step 13: Add the section 2.8 metrics harness (issue #49) — a small tool (`tools/metrics/`) that measures cold start (< 300 ms), idle memory with the `minimal` build (< 80 MB), event delivery latency p99 (< 50 ms), and tool-call overhead (< 5 ms), writes a report (Markdown + JSON), and exits non-zero when a target is missed (1) or a metric cannot be measured (2). Record the measured values in `docs/spec/product.md` §2.8 and mark #49 accordingly. A sample run on the dev container (Linux, Dart 3.14.1 JIT) recorded: cold start 259–880 ms (JIT/container variance; the < 300 ms target is defined for the AOT build), idle memory not measured (the JIT dev-process baseline of ~290–297 MB already exceeds the 80 MB AOT minimal-build target, so the metric degrades to "not measured" rather than a category error), event delivery latency p99 0.00 ms (pass), tool-call overhead p99 0.04–0.15 ms (pass). The harness and its numbers are environment-specific; the recorded values are in the generated `tools/metrics/report.md`/`report.json`.
- [ ] Step 14: Implement the `doctor` checks in `runtime/cli` — daemon reachable, token and its rights, configuration validity, extension signatures, provider availability, `llama-server` `GET /tools` empty (tolerate a 404 as a warning, fail on a non-empty list; Q20), and that the binary's contents match its `distribution.yaml`. TLS and token-strength checks stay M4b. Tests: `runtime/cli/test/doctor_test.dart` with a fake daemon and fake `llama-server` (including the 404 case).
- [x] Step 15: Add the e2e local-mode test in `e2e/test` and verify T11 — start a real daemon on a temporary `ALTERIONE_HOME`, a real client, and a fake `LlmPort`; complete a chat and an SSE replay; assert identical API behavior to the unit-level server. Verify that the `alterione` binary can be produced per OS with `dart build cli`, falling back to `dart compile exe` where it is unavailable, and record the result for T11. Tests: `e2e/test/alteri_one_e2e_test.dart`.

## Outcome

To be filled as steps land. Record here what was done, what was postponed (for example T20 registration if it slips to a manual gate), and any decision that changed — including the Q16 ADR and the measured section 2.8 metrics.

- Step 13 (metrics harness, #49): `tools/metrics/` measures the four section 2.8 targets against a real `Daemon` on a temporary `ALTERIONE_HOME` with a fake `LlmPort`, writes a Markdown + JSON report, and exits non-zero on a missed target (1) or an unmeasurable metric (2). Cold start and idle memory are environment-specific on the JIT dev container (cold start varies with JIT/container load; idle memory degrades to "not measured" because the JIT baseline already exceeds the AOT minimal-build target); event latency and tool-call overhead are well within target. The AOT minimal-build numbers remain to be recorded once a minimal binary exists (M4 personal-build work).
- Step 15: the e2e local-mode test (`e2e/test/alteri_one_e2e_test.dart`) drives a real `Daemon` on a temporary `ALTERIONE_HOME`, a real `AlteriOneClient`, and a fake `LlmPort`: it completes a chat run and consumes `RunFinished` over SSE, replays from `since` with no gap or duplicate, and checks `/v1/info` plus a 401 without a token. It runs in this container with `flutter pub run test` in `e2e` (`dart test` hits the workspace Flutter wall). The test surfaced two real Step 7 defects, fixed here: the SSE `_flush` required a contiguous `seq` and stalled on the first model call (the shared journal counter of ADR-0021 leaves non-lifecycle gaps), and `sseResponse` did not set `shelf.io.buffer_output: false`, so a real `shelf_io` server buffered the never-ending stream and never flushed a frame. T11 is recorded above: `dart build cli` and the `dart compile exe` fallback both produce a runnable `alterione` on Linux; macOS/Windows remain a manual per-OS gate.
