# 0022. Extension message frames are schemantic models

- Status: Accepted
- Date: 2026-11-27

## Context

The extension host and the SDK exchanged messages as hand-rolled
`Map<String, Object?>` literals with manual `jsonEncode`/`jsonDecode` and a
`kind` string switch: the SDK's `runExtension`/`ExtensionRuntime` (M5 Step 3)
built `{kind: 'call', ...}` maps by hand, and the host's
`IsolateExtensionTransport` (M5 Step 7) read and wrote the same maps. The Step 7
implementation deliberately diverged from the spec's "newline-delimited JSON"
wording because the `hello` frame carries a `SendPort`, which is not
JSON-serializable, so the wire shapes were native Dart maps rather than JSON.

The owner requires typed models with generated encode/decode (schemantic
`^1.0.0`, the repository standard) instead of hardcoded maps. The maps gave no
schema, no single source of truth for the frame shape, and no generated
round-trip to test against.

## Decision

The extension message frames are schemantic `@Schema` models in
`packages/contracts/lib/src/frames.dart`, generated by `build_runner` into
`frames.g.dart`: `HelloFrame`, `CallFrame`, `CallResultFrame`, `CallErrorFrame`,
`CancelFrame`, and `EventFrame`. Each carries a `kind` discriminator whose
string values are exactly the ones the existing code used
(`hello`/`call`/`call.result`/`call.error`/`cancel`/`event`), so the wire bytes
are unchanged. The SDK (Step 3) and the host transport (Step 7) construct frames
with the generated constructors and `toJson()`, and parse them with `fromJson()`.

The extension's reply `SendPort` is not JSON-serializable, so it stays a native
field outside the schemantic model: the `hello` frame keeps its native
`{kind, port}` envelope, with the `SendPort` read beside the `kind` discriminator
and the manifest verified separately by the host's `ManifestVerifier`.
`EventFrame` carries the serialized `AgentEvent` as a raw JSON object, because
`AgentEvent` is a hand-written sealed hierarchy with its own `type` discriminator
and `toJson`/`fromJson` that schemantic does not generate.

This resolves the Step 7 native-`Map` deviation: every frame is now a typed
model with generated encode/decode; only the `hello` `SendPort` is native.

## Alternatives

- Keep hand-rolled `Map<String, Object?>` literals: rejected; no schema, no
  single source of truth, and no generated round-trip to verify, which is what
  the owner asked to remove.
- Use `built_value`: rejected; the repository standard for generated
  encode/decode is schemantic (ADR-0015, `docs/spec/architecture.md` §6), and
  adding a second code generator would split the serialization stack.
- Put the `SendPort` inside `HelloFrame`: rejected; a `SendPort` cannot be
  JSON-serialized, so it would force a non-JSON field into an otherwise
  JSON-shaped model and break the generated schema.
- Move the manifest onto the `hello` frame and read it host-side: rejected for
  now; `runExtension(host, register)` has no manifest parameter (changing that
  is an SDK public-API change needing owner sign-off), and the host already
  verifies the manifest through `ManifestVerifier`. `HelloFrame` still models the
  manifest for when the SDK carries one.

## Consequences

- `packages/contracts` gains `frames.dart` (+ generated `frames.g.dart`) and a
  minor version bump; the frame JSON shapes are additive-only and golden-tested.
- `packages/sdk` and `runtime/core` depend on the new contracts minor and build
  and parse frames through the generated models; the wire bytes are identical,
  so the existing isolate and transport behavior tests pass unchanged.
- `tools/codegen_check` regenerates `frames.g.dart`; the file is committed.
- The `hello` `SendPort` remains the one native field, documented at both the
  SDK and transport call sites.
