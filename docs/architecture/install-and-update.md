# Installation, update and the install root

**Status:** Accepted

The core, its extensions and its runtime are installed as one verified release. There are
two front ends — a shell script and a pub.dev bootstrap — and one implementation behind
them. This document is normative for the file layout, the verification order, the atomicity
rule and the failure behaviour. See
[ADR-0017](../decisions/0017-aot-snapshot-and-runtime.md) and
[ADR-0018](../decisions/0018-bootstrap-package.md).

## 1. The two installation paths

| Path | Requires | Command |
|---|---|---|
| Shell installer | a POSIX shell, PowerShell or `cmd` | `sh install.sh`, `pwsh install.ps1`, `install.cmd` |
| Bootstrap CLI | a Dart SDK | `dart pub global activate alterione` then `alterione install` |

Both do the same six steps, in the same order, over the same release manifest. The shell
scripts are generated translations of the bootstrap's plan, and the release pipeline
asserts that they produce an identical file set for the same release — the shell path is
not allowed to become a second, drifting implementation.

```text
resolve target  →  fetch manifest  →  verify signature  →  stage  →  verify digests  →  swap
```

An install reaches exactly one origin: the release host named on the command line. There
is no analytics call, no crash report and no version ping, and the offline release gate in
task `6.10` asserts zero unexpected egress from a run.

## 2. The install root

```text
~/.alterione/                        # $ALTERIONE_HOME, default ~/.alterione
├── alterione                        # launcher — executable, add this directory to PATH
├── alterione-update                 # update
├── install.sh | install.ps1 | install.cmd
├── alterione.aot                    # the compiled release
├── alterione.yaml                   # the shipped manifest: runtime, api, extensions
├── manifest.json                    # versions, SHA-256 digests, signatures
├── bin/
│   └── dartrantime                  # the pinned AOT runtime, downloaded at install time
├── apps/                            # mirrors the source subprojects
│   └── cli/
├── tools/                           # Tier 2 tool executables and Tier 0 data
├── injections/                      # Tier 0 skill packs, Tier 2 injection executables
├── plugins/                         # Tier 2 plugin executables
├── config/                          # profiles/, policies.d/, config.yaml
├── state/                           # runtime state, see workspace-layout.md
└── logs/
```

Three properties of this layout are deliberate:

1. **The four subproject directories mirror the repository.** A user reading
   `~/.alterione/tools/fs/` is looking at the same kind of thing as `tools/fs/` in the
   source, so the deployed payload of every declared extension has one place to live and
   one digest record.
2. **No `alteri_one` survives.** No installed path, launcher, script or default
   configuration value contains it. The repository keeps `alteri_one_*` because that is
   Dart convention; the product does not, because that is what the user sees. Task `0.31`
   fails the release assembly if the string appears.
3. **`alterione.yaml` is the shipped manifest**, copied verbatim from the repository root.
   It is the same `kind: AlteriOneManifest` a project uses, minus the optional `profile`
   block, and it is covered by the release signature.

### 2.1 The launcher

The launcher is named `alterione` — not `run`, not `start`, not `alterione.sh` — so that
adding the install root to `PATH` is the whole installation story:

```sh
#!/bin/sh
# alterione — generated by the installer. Runs the compiled release on the pinned runtime.
set -eu
home=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)
[ -n "${ALTERIONE_HOME:-}" ] && home="$ALTERIONE_HOME"
exec "$home/bin/dartrantime" "$home/alterione.aot" "$@"
```

It resolves its own directory, so it works from any working directory, and it honours
`ALTERIONE_HOME` when it is set. `alterione-update` is the same script with the update
step substituted. On Windows the installer writes an equivalent `alterione.cmd` wrapper
that performs the same two checks before `exec`.

## 3. The pinned Dart runtime

The runtime binary itself is `bin/dartrantime`. It is **not** the Dart SDK: it carries no
`pub`, no compiler and no development tooling, because those are exactly the capabilities
a Tier 2 child must never inherit.

| Property | Value |
|---|---|
| Downloaded | by the install script and by `alterione install`, from the release host |
| Verified | SHA-256 against `manifest.json`, which is covered by the release signature |
| Version requirement | `alterione.yaml` → `runtime.version`, narrowed to the snapshot's major.minor |
| Mismatch | refused with exit code `9`; never a system `dart`, never JIT, never source |
| Cached | `bin/` is replaced wholesale on update; the old runtime is removed, not kept |

The narrowing matters and is not cosmetic. A Dart AOT snapshot is not forward compatible
across minor versions: a snapshot built by 3.13 executes on a 3.13 runtime and on no
other. The workspace SDK constraint is therefore written `>=3.13.0 <4.0.0` everywhere in
the source, while the shipped `runtime.version` is narrowed to `>=3.13.0 <3.14.0` by the
release tooling. A runtime outside that range is an integrity failure, not a warning, and
there is no degraded mode.

```bash
alterione which        # install root, release version, runtime version and digest
alterione doctor       # full check, including the runtime digest and the api.* agreement
```

## 4. Install and update

### 4.1 `install.sh`

```bash
curl -fsSL https://github.com/dip-develop/alteri-one/releases/latest/download/install.sh -o install.sh
less install.sh        # read before running; it is the thing that writes to your disk
sh install.sh
```

Flags, all optional:

| Flag | Effect |
|---|---|
| `--dir <path>` | Install root. Default `$ALTERIONE_HOME` or `~/.alterione` |
| `--channel <name>` | `stable` (default) or `beta` |
| `--version <semver>` | Exact release. Mutually exclusive with `--channel` |
| `--target <triple>` | `linux-x64`, `darwin-arm64`, `darwin-x64`, `windows-x64` |
| `--no-runtime` | Skip `bin/dartrantime`. Only for an offline copy that already has one |
| `--force` | Reinstall over an existing tree. Still atomic, still verified |

The script never requires elevation. A system-wide install is a choice an operator makes
by passing `--dir /opt/alterione`; the default is a user directory.

### 4.2 `alterione install`

```bash
dart pub global activate alterione
alterione install                    # latest stable
alterione install --version 1.2.0
alterione update                     # same resolution, current channel
alterione update --check             # report what an update would do, change nothing
alterione run -- --profile companion # exec the installed launcher
alterione which                      # which command, install root, versions, digests
alterione version
```

`alterione install` performs the same six steps as the shell script and exits with the
same codes. It never executes extension code, never runs the release during installation,
and never reaches an origin other than the release host.

### 4.3 The six steps

1. **Resolve the target.** Explicit triple, or detected platform and architecture. An
   unsupported platform is a refusal, not a source build.
2. **Fetch the manifest.** `manifest.json` from the release, carrying the release version,
   the `alterione.aot` digest, the `dartrantime` digest, the `alterione.yaml` digest and
   the signature.
3. **Verify the signature** of the manifest. A missing or unverifiable signature stops
   here, before a single byte is written.
4. **Stage** into `<root>/.staging-<pid>/`: the snapshot, the manifest, the shipped
   `alterione.yaml`, `bin/dartrantime`, the launcher, the update script and the installer
   itself.
5. **Verify every staged file** against the digests in the manifest. A mismatch deletes the
   staging directory and exits `9`.
6. **Swap.** Move the staged tree into place, preserving the previous installation as
   `<root>/.previous/` until the first successful launch, then remove it.

### 4.4 Atomicity and idempotence

- A failure at any step leaves the previous installation byte-for-byte unchanged. There is
  no state in which half the release is present.
- `install` twice is a no-op that re-verifies. It does not accumulate files and does not
  re-download what already matches its digest.
- `update` is `install` with a version resolved from the channel, and it keeps the same
  guarantee.
- `update --check` and `doctor` are read-only and perform no writes beyond an explicit
  cache refresh.

### 4.5 What an update does and does not touch

| Updated | Untouched |
|---|---|
| `alterione.aot`, `alterione.yaml`, `manifest.json` | `config/` |
| `bin/dartrantime`, when the range requires it | `state/`, `logs/` |
| the launcher, the update script, the installer | installed Tier 0 injections and Tier 2 executables |
| | profiles and policies |

A release may also ship new Tier 2 executables or a new Tier 0 pack under the subproject
directories; those are added with a digest record and are never replaced in place while a
process may hold them open.

## 5. Verification at launch

The launcher and `doctor` re-check, in order:

| Check | Failure |
|---|---|
| `bin/dartrantime` present and its digest matches `manifest.json` | exit `9`, `integrity.integrity_failed` |
| `dartrantime` version inside `runtime.version` | exit `9`, `integrity.runtime_mismatch` |
| `alterione.aot` digest matches the manifest | exit `9`, `integrity.integrity_failed` |
| `alterione.yaml` parses, and its `apiVersion` is known | exit `3`, `config.unknown_api_version` |
| every enabled extension resolves in the compiled registry | exit `3`, `extension.unresolved` |
| every extension's `apiVersion` is inside `api.extension` and its port inside `api.ports` | exit `3`, `extension.version_incompatible` |

No check has a degraded outcome. A missing, stale or unverified runtime never falls back
to a system `dart`, to JIT or to running from source — a JIT fallback would silently
remove the property the whole tier model rests on.

## 6. Adding extensions to an installed product

The split is the one in [ADR-0015](../decisions/0015-extension-dependencies.md), and it
is worth stating plainly because it is the part users get wrong:

| You want to… | What it takes |
|---|---|
| Add a third-party **tool, injection or plugin** (Tier 1) | a dependency in `pubspec.yaml`, an entry in `alterione.yaml`, a rebuild — Dart has no class loader |
| Add a third-party **skill pack** (Tier 0) | copy the pack into `~/.alterione/injections/<id>/`; it is data, verified by digest, never executed |
| Add a third-party **Tier 2** tool or plugin | place the signed executable and its manifest in `~/.alterione/{tools,plugins}/<id>/`; the sandbox host verifies and starts it |
| Remove any of the above | delete the dependency from `pubspec.yaml` and the entry from `alterione.yaml` and rebuild, or delete the deployed directory |

The command surface is `alterione injections list|verify` and `alterione plugins
list|verify` — see [apps/cli.md](../apps/cli.md). There is deliberately no
`alterione extensions add <name>` for compiled code: an interface that implies runtime
loading of Dart code is an interface that cannot be implemented.

## 7. Uninstallation

`install.sh --uninstall` and `alterione uninstall` remove the release, the runtime and
the deployed extension payloads. They never remove `config/` or `state/` unless
`--purge` is given, and `--purge` prints exactly what it will delete before doing it.
State is the user's transcripts, memories and profiles; an uninstall that takes them
without saying so is a data-loss bug wearing a convenience costume.
