| Q12 | ~~An approval refusal is not journalled: section 9 writes `denied` only for policy denials, so `not_approved` leaves no audit record although it stops a side effect. Should a refusal be recorded?~~ Resolved 2026-11-19: yes. See [ADR-0016](../adr/0016-interactive-approval-channel.md). | resolved |
| Q13 | ~~Section 8.10 rule 2 lists "model call, tool call, channel send" as effects that must be journalled before they run, but the section 9 loop calls `d.llm.complete(...)` without a journal record and the section 9 snippet omits one. | Q14 | A timed-out tool cannot be cancelled by `Future.timeout`. Must a call that may still complete be recorded as `unknownOutcome` instead of `failed`? Section 9 writes `failed`. | keep `failed` (section 9); cancel a per-invocation child token and leave the run token alone |
| Q15 | Transcript persistence: [ADR-0012](../adr/0012-model-call-journaling.md) assigns it to the `JournalingLlm` decorator, but the agent loop owns the mutable message list (it appends assistant turns and tool results) while the decorator only sees the messages of each model call and never the tool results, and the journal deliberately stores no prompt or reply text (section 15.6 of `storage.md`). Which component owns the transcript, and what is its write protocol? | not implemented in M2; `RunService` leaves a documented seam and does not fake a transcript; revisit in M3/M4 |
| Q16 | ~~Run lifecycle is not journalled: `RunStarted`, `RunFinished` and the approval events have no journal record, so `RunStarted.seq`, `ApprovalRequested.seq` and `ApprovalResolved.seq` are `null`, and `RunFinished.seq` is only the last effect `seq` (best effort). See [ADR-0021](../adr/0021-run-lifecycle-journal-record.md). | resolved |
| Q17 | ~~Concurrent approvals: the agent loop runs a turn's tool calls with `Future.wait`, so two tool calls that both need approval start two concurrent `ask`s; `RunBloc` holds a single pending approval, so the second request and its resolution would raise `InvalidTransition`. Serialize approvals per run, or extend the state and the bloc to hold several pending approvals?~~ Resolved 2026-11-19: serialize per run. Every approval of a run goes through one `SerialQueue`, so the second request is journalled and asked only after the first is resolved; the bloc keeps its single `pendingApproval`. See [ADR-0016](../adr/0016-interactive-approval-channel.md). | resolved |
| Q18 | ~~What does "interactive channel" mean concretely for M2? Real transports (socket, IPC) land in M4. See [ADR-0016](../adr/0016-interactive-approval-channel.md). | resolved |
| Q19 | ~~Real-`llama-server` conformance is a scheduled follow-up (M3 part 2, ADR-0018); a fake OpenAI-compatible server runs in every PR. | Q20 | ~~`GET /tools` is upstream-unstable: the endpoint and its schema change across `llama-server` builds, so `doctor` cannot rely on it to enumerate the server's built-in tools.~~ Resolved 2026-11-22: `doctor` does not rely on `GET /tools` to enumerate tools; it tolerates a 404 (warn, not fail). See [ADR-0018](../adr/0018-llm-provider-contract-and-llamapulse-adapter.md) and `docs/spec/providers.md` §12.3. | resolved |
| Q21 | `native_tools: auto` is resolved by a probe and by the conformance suite, which can disagree on whether the model emits native tool calls. | `auto` resolves to `false` if the probe and the suite disagree |
| Q22 | ~~A schema-less `ToolSpec.inputSchema == null` gives the provider no `parameters` to send; the server then applies its own default for the argument schema.~~ Resolved 2026-11-22: the provider sends no `parameters` member and accepts any arguments; the server applies its own default for the argument schema. | Q23 | ~~`LlmUnavailable` is logged and journalled, and a local server's response body can echo fragments of the prompt.~~ Resolved 2026-11-22: `LlmUnavailable` carries the HTTP status only, never a response body or a secret.
